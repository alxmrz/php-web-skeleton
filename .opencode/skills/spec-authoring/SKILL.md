Правила о том, как писать документы для реализации агенту: что попадает в спеку,
что в дизайн, как имена связываются с кодом и как режется работа.

Скилл не привязан к конкретному SDD-инструменту. Названия файлов
(`proposal.md`, `spec.md`, `design.md`, `tasks.md`) — условные: подстраивайся под
те, что задаёт проект или фреймворк.

## Когда применять

- Пишешь или правишь `proposal.md`, `spec.md`, `design.md`, `tasks.md`.
- Разбираешь чужую спеку, чтобы её дополнить или согласовать с дизайном.
- Готовишь нарезку задач перед передачей работы агентам.

Не применяй для кода без планирования и для чисто технических рефакторингов,
где наблюдаемое поведение не меняется.

## Приоритет источников

1. **Формат задаёт шаблон, а не скилл.** Обязательные секции, операции над
   требованиями, разметка сценариев — берутся из шаблона проекта или вывода CLI
   фреймворка. Скилл описывает *технику*, а не синтаксис.
2. **Проектное правило сильнее общей рекомендации фреймворка.** Типичный случай:
   фреймворк советует не упоминать внутренние имена классов в `spec.md`, а проект
   требует таблицу API с полными именами. Побеждает проект; технику применяй в
   рамках этого правила.
3. **Явное решение пользователя сильнее скилла.** Озвучь конфликт, а не
   подстраивай молча.

Как адаптировать технику под конкретный формат — `references/format-adapters.md`.

## Порядок работы

1. **`proposal.md`** — зачем и что. Перечисли capability-границы: какие
   способности системы появляются или меняются. Пути должны быть устойчивыми
   именами поведения (`user-auth`), а не именами работ (`add-login-endpoint`).
2. **`spec.md`** — что система обязана делать. Одно правило = один Requirement;
   у правила минимум позитивный и негативный/граничный сценарий. После сценариев
   — три таблицы: изменений (`Файл | Класс | Метод | Действие | Что меняется`),
   полная таблица тестов (`Файл тестов | Тестовый метод | Что проверяет`) по всем
   модулям изменения и таблица API.
3. **`design.md`** — как. Диаграммы процессов, последовательности, классов,
   схема БД. Ссылки на принятые решения и их причины.
4. **`tasks.md`** — в каком порядке и кто. Задача = связный кусок над своим
   набором файлов; зависимости помечены.

Методика вывода сценариев и формулировок — `references/spec-techniques.md`.
Связь имён между артефактами — `references/traceability.md`.
Диаграммы — `references/design-diagrams.md`.
Нарезка — `references/tasks-slicing.md`.

## Что куда

| Артефакт | Отвечает на вопрос | Не содержит |
| --- | --- | --- |
| `proposal.md` | Зачем это нужно, что меняется, что затронуто | Сценариев, диаграмм, пошагового плана |
| `spec.md` | Что система обязана делать снаружи | Диаграмм, алгоритмов, выбора библиотек |
| `design.md` | Как устроено: структуры, потоки, решения | Бизнес-требований (только ссылки на них) |
| `tasks.md` | В каком порядке делать и как проверить | Требований и диаграмм (ссылки, не копии) |

Правило проверки: если реализацию можно переписать, не меняя наблюдаемого
поведения, — это не спека, это дизайн.

## Чек-лист ревью

Пройди перед тем, как считать артефакты готовыми.

**Требования и сценарии**

- [ ] В спеке нет сценария без теста и теста без сценария.
- [ ] В одном Requirement — одно поведение, а не два.
- [ ] Нормативные требования используют `SHALL`/`MUST`; `should`/`may` только для
      действительно рекомендательного.
- [ ] На каждое правило есть негативный или граничный кейс, а не только happy path.
- [ ] Сценарий проверяем: понятно, что подать на вход и что считать результатом.

**Границы артефактов**

- [ ] В `spec.md` нет диаграмм, алгоритмов, названий библиотек и шагов реализации.
- [ ] В `design.md` нет пересказа требований — только ссылки и решения.
- [ ] В `tasks.md` нет требований; каждая задача ссылается на сценарии, которые
      закрывает.

**Имена**

- [ ] Таблица изменений покрывает все правки: ни один файл, класс или метод не
      меняется без своей строки.
- [ ] В таблице изменений у каждой строки заполнено действие:
      `добавляется` / `изменяется` / `удаляется`.
- [ ] Новые и изменённые методы даны с полной сигнатурой.
- [ ] Таблица изменений и таблица API согласованы: добавленное есть в обеих,
      удалённое отсутствует в обеих.
- [ ] Имена классов, методов, таблиц и колонок совпадают в `spec.md`,
      `design.md`, `tasks.md` и коде.
- [ ] Публичные методы в таблице API описаны полностью: сигнатура, типы,
      исключения, побочные эффекты.
- [ ] Приватные и внутренние методы в таблицу API не попали.

**Задачи**

- [ ] Одна задача не размазана по файлам другой задачи без пометки зависимости.
- [ ] Общий каркас (интерфейс, контракт, точка входа) вынесен в предшественника.
- [ ] Тесты живут в задаче, реализующей правило; отдельной «финальной задачи на
      тесты» нет.
- [ ] У каждой задачи есть изолированная проверка, не требующая ждать остальные.

## Анти-паттерны

| Анти-паттерн | Почему плохо | Как исправить |
| --- | --- | --- |
| «Система должна работать быстро» | Не проверяется | Задай измеримый порог и условие замера |
| Один Requirement на весь модуль | Непонятно, какой тест что закрывает | Разбей по наблюдаемым правилам |
| Сценарий «пользователь делает всё» | Один тест на десять правил | Один сценарий — одна проверяемая мысль |
| Скопированная диаграмма в `spec.md` | Два источника истины | Оставь в `design.md`, поставь ссылку |
| Таблица API, расходящаяся с кодом | Ломает трассируемость | Обновляй таблицу в той же задаче |
| Правка кода без строки в таблице изменений | Объём работы скрыт, трассируемость рвётся | Добавь строку или откати правку |
| Задача «доделать всё остальное» | Не параллелится, скрывает объём | Выдели каркас и конкретные модули |
| Тесты отдельной финальной задачей | Правило живёт без проверки до конца | Перенеси тесты в задачу-реализатор |

## Стоп-сигналы

Остановись и спроси, если:

- непонятно, меняется ли наблюдаемое поведение (значит, непонятно, нужна ли спека);
- правило нельзя превратить в проверяемый сценарий;
- требования конфликтуют с существующей спекой, и неясно, какое главнее;
- формат шаблона противоречит проектному правилу — такой выбор нельзя делать молча.
